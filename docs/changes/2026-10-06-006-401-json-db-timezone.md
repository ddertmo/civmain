# API returns 401 JSON instead of a 500 HTML page; DB session timezone aligned with the app

- **Date:** 2026-10-06
- **Commit:** `fc497bd`
- **Type:** fix
- **Areas:** Laravel

Two unrelated-but-both-live bugs fixed together.

---

## Bug A — protected API routes returned 500 HTML instead of 401 JSON

### Problem

Any `GET/POST` to a protected route with a missing, expired or bad token
returned **HTTP 500 with the CivilWatch admin HTML page as the body** instead of
a 401 JSON error. A mobile client parsing JSON got a parse error and no clue
what was wrong.

Repro before the fix:
```
curl /api/mobile/reports              → 500, <!DOCTYPE html>
curl /api/mobile/reports -H 'Authorization: Bearer bogus' → 500, <!DOCTYPE html>
```

### Cause

Laravel's `Illuminate\Auth\Middleware\Authenticate` middleware calls
`redirectTo()` when the request "should not render JSON". This app has **no
named `login` route** (it is API-only), so the redirect target
`route('login')` threw `RouteNotFoundException: Route [login] not defined`,
which surfaced as a 500 and fell through to the admin error page.

### Changes

| File | Change |
|---|---|
| `laravel/bootstrap/app.php` | in `->withExceptions(...)`, added `$exceptions->shouldRenderJsonWhen(fn ($request) => $request->is('api/*') \|\| $request->expectsJson())` so API requests get JSON errors and are never redirected |

### Verification

```
GET /api/mobile/reports                → {"message":"Unauthenticated."}  [401]
GET /api/mobile/reports (bad bearer)   → {"message":"Unauthenticated."}  [401]
```

## Bug B — report activity timestamps were 8 hours apart

### Problem

One report produced two activity rows written in the same request that were
**8 hours apart**:

```
Report Submitted    → 2026-10-06 05:49:54   (written by PHP `now()`)
Pending Validation  → 2026-10-06 13:49:54   (written by MySQL CURRENT_TIMESTAMP)
```

Citizens saw a nonsensical timeline.

### Cause

The app timezone is **UTC** (`config/app.php`) but the MariaDB session timezone
was `SYSTEM` = **UTC+8**. Laravel writes `now()` as a UTC wall-clock string,
while `report_activities.created_at` defaults to MySQL's `CURRENT_TIMESTAMP`,
which MySQL renders in the session timezone. Both round-trip through the
`TIMESTAMP` column differently, so reads disagreed by exactly 8 hours.

### Changes

| File | Change |
|---|---|
| `laravel/config/database.php` | added `PDO::MYSQL_ATTR_INIT_COMMAND => "SET time_zone = '+00:00'"` to both the `mysql` and `mariadb` connections, guarded with `PHP_VERSION_ID >= 80500 ? Mysql::ATTR_INIT_COMMAND : ...` to avoid a PHP 8.5 deprecation notice |

Then `php artisan migrate:fresh --seed --force` to rebuild the dev data with
consistent timestamps.

### Verification

```
SELECT NOW(), @@session.time_zone   → 2026-10-06 06:10:16, +00:00
php: now()                          → 2026-10-06T06:10:16+00:00   (identical)

report activity log after submit:
  Report Submitted    -> 2026-10-06T06:15:22+00:00
  Pending Validation  -> 2026-10-06T06:15:22+00:00   (was +8h)
```
No PHP deprecation warning emitted.

## Impact / how to test by hand

```bash
# A: expect 401 JSON, never HTML
curl -s http://127.0.0.1:8000/api/mobile/reports -H 'Accept: application/json'

# B: submit a report, then check both activity rows share a timestamp
mariadb --socket=$HOME/.local/var/mysql/mysql.sock -u root -D civilwatch \
  -e "SELECT title, created_at FROM report_activities ORDER BY id DESC LIMIT 2;"
```
